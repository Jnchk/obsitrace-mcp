# Obsidian Worklog与总结技能需求分析报告

- **状态：** 需求已确认并完成首版实现；部署前需核对目标 Vault
- **日期：** 2026-11-09
- **目标：** 创建一个以 Obsidian 为Worklog来源、由 Skill 提供自然语言交互、由 Go 版 Obsidian MCP 承担数据筛选和自动化的工作管理与总结能力。

## 1. 背景与目标

用户希望随时用自然语言记录待办、更新进度、标记完成，并查看本日、本周、本月、本年度及全部记录期间的工作进展，用于个人回顾和汇报。任务和工作事实保存在 Obsidian Vault 中。

系统应做到：

1. 记录与更新快捷，不为可选信息反复追问。
2. 任务当前状态清晰，进展和状态变化可回溯。
3. 不同时间范围的总结采用统一边界，结论能追溯到原始记录。
4. 通过 MCP 服务端筛选和聚合，只把与请求相关的精简结果返回模型，减少上下文/token 消耗。
5. 遇到歧义、写入冲突或部分失败时明确询问或报告，不猜测、不伪报成功。

## 2. 技术方案

### 2.1 职责划分

采用“**Skill 交互与编排 + Go MCP 服务端数据操作与聚合 + Obsidian Markdown 数据**”：

- **Skill（`SKILL.md`）**：识别用户意图、决定调用哪个 MCP 工具、在任务不明确时澄清，并把工具返回的事实组织成可读总结。
- **Go MCP 服务端**：在 Vault 本地读取、筛选、更新笔记；实现状态变更、日期范围查询及紧凑结果返回等确定性逻辑。
- **Obsidian Vault**：保留人可读、可编辑、可链接的任务、日志和总结笔记。
- **Skill 附带代码**：不是连接 MCP 的客户端。只有在有明确收益时，才加入不依赖 Vault 访问的轻量辅助脚本，例如日期/模板验证；初始阶段不把重复的数据筛选逻辑放进 Skill 脚本。

### 2.2 选择 Go 的依据与 MCP 边界

项目根目录是 Go 模块，使用 `github.com/modelcontextprotocol/go-sdk` 注册工具；服务通过 `mcp.StdioTransport` 与 MCP 宿主通信。除现有笔记工具外，已增加专用Worklog工具。Worklog使用的 IANA 时区通过 `mcp-config.json` 对应 MCP server 的 `env.OBSIDIAN_TIMEZONE` 设置，由宿主传入服务进程；默认值为 `Asia/Shanghai`。该配置由 MCP 部署配置提供，不要求 Skill 自行连接服务。

Skill 不能仅凭当前 MCP 工具定义，另起 Python/TypeScript 客户端直接访问宿主的 stdio 连接；服务端没有向 Skill 脚本暴露可复用的网络端点或认证信息。因此，凡是为了减少模型上下文而进行的筛选、范围读取和结果压缩，必须在 Go MCP 工具调用内部完成。这样宿主只接收精简输出，而不是先把全库内容交给模型再过滤。

当前 `search` 会在服务端搜索 Markdown 文件，但输出仍是通用全文匹配结果，不具备任务状态或时间范围语义；当前 MCP `write` handler 固定使用覆盖模式，虽然底层文件服务还支持 append/prepend，MCP 调用者并不能使用这些模式。具体实现时需考虑这些现状，不能假设现有接口已提供专用的安全追加或汇总能力。

### 2.3 Obsidian 数据组织

采用“**总任务索引 + 每项任务详情笔记 + 每日日志 + 按需保存的周期总结**”：

- **总任务索引**：任务日常查询入口，包含紧凑、可解析的任务 ID、标题、状态、项目（如有）、创建/更新/完成日期、截止日期（如有）及详情笔记路径。
- **任务详情笔记**：保存任务说明和带日期的进度/状态变化历史。
- **每日日志**：保存当天完成内容、结果、进展、阻塞/风险、下一步，并链接相关任务。
- **周期总结**：按需生成的派生笔记，包含来源日志/笔记链接，可用于后续年报或全期间回顾；不作为任务当前状态的权威来源。

建议初始目录结构如下：

```text
Worklog/
├── Index/
│   ├── Task Index.md
│   ├── Task Done.md
│   └── Task Ongoing.md
├── Tasks/
│   └── <project>/
│       └── <task-id>.md
├── Logs/
│   └── YYYY/
│       └── MM/
│           └── YYYY-MM-DD.md
└── Summaries/
    ├── Daily/
    ├── Weekly/
    ├── Monthly/
    ├── Yearly/
    ├── All Time/
    └── Custom/
```

新任务详情存放于 `Worklog/Tasks/<project>/<task-id>.md`，其中 `<project>` 是用户在对话中提供或确认的项目名称；未提供项目时先询问，不创建 `Project` 或 `Unassigned` 等默认目录。已有任务详情保持原路径，不因新增状态列表而移动。

`Index/Task Index.md` 展示所有任务；`Index/Task Ongoing.md` 是待办、进行中和阻塞任务的动态列表；`Index/Task Done.md` 是已完成和已取消任务的动态列表。MCP 服务在任务创建或更新时同步刷新三个页面，后两个页面为总索引的派生视图。

总任务索引是任务当前状态的权威来源；Go MCP 服务在本地读取索引并完成筛选，只向模型返回匹配任务，不要求模型扫描或读取整个任务目录。只有用户要求详情或索引不足以确认任务时，才读取相应任务笔记。索引格式必须能被 Obsidian 正常阅读，也能由 Go 稳定解析和更新；具体 Markdown/frontmatter 格式在实现设计阶段确定。

### 2.4 建议新增的 MCP 工具

在现有通用笔记工具之外，优先评估并实现以下面向Worklog的聚合工具：

| 工具（建议名） | 职责 | 返回原则 |
|---|---|---|
| `query_tasks` | 按 ID、关键词、状态、项目等查询总任务索引 | 只返回匹配任务的简洁字段及必要路径，不返回完整索引或整个目录 |
| `create_task` | 创建任务详情、索引行和创建日志事件；重复标题先返回候选 | 由请求 UUID 生成稳定任务 ID；新建前询问重复候选 |
| `update_task` | 更新单项任务状态/字段、追加详情历史并登记日志事件 | 对同一 requestId 的重试避免重复事件，写入失败明确返回 |
| `record_work` | 将独立或关联任务的工作事实追加到指定日期日志 | 校验日期和任务引用；不存在索引时按需初始化 |
| `get_work_summary` | 按日、周、月、年、全期间或自定义范围读取工作事实 | 返回范围、时区、来源路径、当前未完成任务和截断标记 |
| `save_work_summary` | 按需保存用户要求的总结 | 校验来源摘要，只新建文件，不覆盖已有笔记 |
| `sync_tasks` | 从每个任务详情的 H1 同步任务标题到总索引，并刷新待办/完成视图 | 显式调用；全部详情校验通过后才更新，返回标题变更数及路径 |

工具输入应聚焦于用户意图所需字段，避免要求模型重复提交整篇笔记。更新操作须有稳定任务 ID 或经查询确认的唯一目标；创建前检查明显重复项。工具的精确 schema、错误码和索引格式由 MCP 实现设计确定。

周/月总结读取所需期间的日志；年/全期间总结可以在服务端本地读取必要日志和任务索引，返回有限的精简事实；用户确认需要持久化时，再创建带来源路径及摘要校验信息的汇总笔记。不得为单次总结把全库笔记内容返回给模型。

### 2.5 一致性与写入策略

创建/更新任务通常涉及索引与详情笔记两处写入，而当前文件服务没有跨多笔记事务。实现必须明确处理顺序、错误和重试：

- 每次写入均报告具体结果；部分写入时返回可辨识的部分失败信息及已完成步骤。
- Skill 不得把部分成功描述为全部成功；在状态未确认一致前不继续生成依赖该写入的成功总结。
- 重试更新时避免重复追加同一条进展记录；实现可使用稳定事件标识或等效的幂等策略。
- 追加/更新路径应先区分文件不存在与权限、解析等其他错误；不得把任意读取错误都当作新文件处理。
- 默认不删除任务、不覆盖无关日志内容、不移动已完成任务。

## 3. 用户与使用场景

主要用户为希望持续记录工作并定期回顾、汇报的个人用户。

1. **记录待办**：“记一下，下周三前完成客户数据核对。”
2. **更新进度**：“客户数据核对已经完成 70%，差异项还在确认。”
3. **记录当天工作**：“今天完成了接口联调，发现两个边界问题，关联到支付项目。”
4. **变更状态**：“把接口联调标记为完成，结果是测试环境通过。”
5. **查看进展**：“总结我今天/本周/本月/今年做了什么。”
6. **准备汇报**：“给我一份适合发给主管的本周工作总结，包含成果、风险和下周计划。”
7. **全期间回顾**：“从开始记录以来，我做过哪些工作？目前还有什么没完成？”

## 4. 功能需求

### 4.1 任务管理

- 从自然语言识别任务标题和用户明确提供的截止日期、项目、优先级等信息。
- 创建任务必须确认所属项目，以项目名称建立任务详情子目录。
- 为新任务创建稳定且唯一的 ID；缺少可选信息时先保存最小任务，不因可选字段打断快速记录。
- 创建前利用总索引检查明显重复项；有多个相似候选时先询问，不猜测。
- 支持更新进展、状态、截止日期等；每次进展或状态变化均保留带日期的历史。
- 创建或更新任务时同步刷新全量、未完成和已结束三个任务列表页；未完成列表包含 `todo`、`in_progress`、`blocked`，结束列表包含 `done`、`cancelled`。
- 完成时记录完成日期；已完成任务保留原位置，仅更新状态。
- 支持“已取消”状态；保留记录供历史回顾，不删除。

### 4.2 工作日志

- 按日期记录成果/结果、阶段性进展、阻塞/风险及下一步。
- 日志条目可链接任务和项目；没有对应任务的工作也可独立记录。
- 更新当日日志时保留既有条目，不覆盖用户手动维护的其他内容。
- 可按需生成周、月、年及全期间总结；总结包含原始来源路径或 Obsidian 链接。

### 4.3 查询与总结

- 支持日、周、月、年、全部工作期间及自定义起止日期查询。
- 周期总结默认采用“成果、进行中/阻塞、下一步”结构；可按汇报需要调整语气和重点。
- 区分“在该期间完成的工作”与“当前仍在进行的工作”，不以任务当前状态推断其过去状态。
- 状态包括：待办、进行中、已完成、阻塞、已取消；已取消事项仅在用户要求或历史回顾相关时展示。
- 无对应记录时明确说明未找到记录，不推断或编造。
- 总结用事实应附日期和来源任务/日志，便于核对。

### 4.4 MCP 服务端自动化与 token 控制

- 任务查询由 Go MCP 服务端读取并过滤总索引，模型只接收匹配任务的简要结果。
- 总结工具只读取请求范围所需的日志/已存汇总，在服务端完成范围筛选和结果压缩。
- 日常查询和更新不例行搜索全 Vault 或将整篇索引、详情目录传给模型。
- 工具返回应保留总结所需的事实、日期、状态及来源路径；不能为节省 token 删除可追溯依据。
- 日期计算与格式化等纯确定性逻辑应在服务端复用统一实现，不由 Skill 每次临时推算。

## 5. 数据字段与时间口径

### 5.1 任务索引字段

| 字段 | 必需性 | 说明 |
|---|---|---|
| ID、标题、详情路径 | 必需 | 唯一定位任务、建立 Obsidian 链接 |
| 状态 | 必需 | `todo`、`in_progress`、`done`、`blocked`、`cancelled` |
| 创建日期、更新日期 | 必需 | 排序、筛选和追溯 |
| 完成日期 | 完成时必需 | 统计期间内完成项 |
| 项目 | 必需 | 用户提供或确认；用于任务详情目录 `Tasks/<project>/` |
| 截止日期、优先级 | 可选 | 只记录用户提供或确认的内容 |

### 5.2 任务详情与工作日志

- 任务详情：任务描述及带日期的进度/状态变化记录。
- 每日日志：日期、成果/结果、进行中事项、阻塞/风险、下一步、关联任务/项目。
- 周期总结：总结期间、成果、进行中/阻塞、下一步、数据覆盖说明及来源链接。
- 工作记录的状态、类别、Markdown 标题和目录名使用英文固定标识；用户提供的标题、描述与记录正文可使用任意语言。

### 5.3 日期和总结边界

- 时区：通过 `mcp-config.json` 中 Obsidian MCP server 的 `env.OBSIDIAN_TIMEZONE` 配置 IANA 时区；未配置时默认 `Asia/Shanghai`。无效时区应明确报错，不回退到本机时区。
- 周：周日至周六。
- 月、年：按公历自然月、自然年。
- 全部工作期间：从启用该记录体系/开始记录之日起；总结明确数据覆盖起止日期。
- 总结按工作发生或完成的记录日期归属；对于跨期未完成任务，展示当前状态时标为当前状态，不算作期间内已完成。

## 6. 非功能与安全要求

- **可追溯：** 总结事实可回到任务或日志来源。
- **低上下文消耗：** 过滤和聚合在 MCP 服务端本地完成，只返回必要结果。
- **一致性：** 索引与详情变更的部分失败必须可见、可恢复，重试不重复记录。
- **保守修改：** 不批量改造旧笔记、不删除记录、不覆盖非目标内容；有歧义先询问。
- **透明性：** 报告实际读写路径及结果；MCP 错误不得被包装成成功。
- **渐进采用：** 沿用用户现有 Vault 约定，不要求迁移旧数据。
- **隐私：** 工作内容保存在用户指定 Vault；不发送到无关服务。
- **可测试：** 日期边界、索引筛选、任务状态变更、错误和部分失败均有 Go 自动化测试覆盖。

## 7. 暂不纳入的范围

- 自动访问或同步日历、邮件、工单、代码仓库等外部系统。
- 自动推断未记录的工作内容、绩效结论或任务完成情况。
- 自动删除、归档或批量重构现有 Vault 内容。
- 强制使用特定项目管理方法、进度百分比或评分体系。
- Skill 通过另一个自行配置的客户端直接连接 MCP stdio 服务。

## 8. 验收标准

1. 新建待办时，系统要求项目名称，检查明显重复项，生成稳定 ID，在项目目录创建任务详情，并刷新总索引、`Task Ongoing` 和 `Task Done`。
2. 更新进度或状态后，总索引及两个状态视图正确，详情保留带日期的历史；相同更新重试不会重复追加。
3. MCP 写入任何一处失败时明确返回失败/部分失败和具体路径，不宣称整体成功。
4. 查询任务时由 Go 服务端筛选，只返回匹配任务的精简结果，不把全任务目录或完整索引交给模型。
5. 完成任务会记录完成日期；对应期间总结将其作为该期间完成项，非完成任务不会误计为完成。
6. 日、周、月、年、全期间及自定义范围按 `mcp-config.json` 配置的时区和已确认的周边界工作；未配置时采用 `Asia/Shanghai`，无效配置明确报错。
7. 总结只基于范围内日志/可复用汇总和必要的任务索引；每条关键事实带日期及来源。
8. 无记录、匹配不唯一、索引格式错误、读取权限错误及部分写入等情形均有明确处理，不编造结果。
9. Go MCP 工具的参数、返回结构、日期过滤和错误路径由自动化测试覆盖；Skill 测试覆盖新增、更新、完成、歧义询问及周期总结。
10. 新增任务必须提供合法项目目录名；修改项目时详情路径随之更新，遇到路径冲突不得覆盖已有笔记。
11. 新写日志在 Obsidian 阅读视图中以易读列表显示，隐藏事件元数据仍能支持幂等去重和总结筛选；旧日志格式继续可读。

## 9. 已确认的用户决策

1. 采用每任务一篇详情笔记、每日日志和一个总任务索引。
2. 采用待办、进行中、已完成、阻塞、已取消五种状态。
3. 周日至周六；时区从 `mcp-config.json` 配置，默认 `Asia/Shanghai`；全期间从开始记录之日起算。
4. 保留每次进展/状态变化的带日期历史；不强制填写百分比。
5. 默认总结结构为“成果、进行中/阻塞、下一步”。
6. 项目是必填项；未提供时先询问。缺少截止日期、优先级等可选信息时仍可直接创建任务。
7. 已完成任务留在原位置，只更新状态，不移动归档。
8. 用户认可将数据筛选和自动化逻辑优先实现于现有 Go MCP 服务端；Skill 负责自然语言交互和总结表达，不另建 MCP 客户端。
9. 任务详情新建于 `Worklog/Tasks/<project>/<task-id>.md`；已有任务详情不因增加状态列表而移动。
10. `Worklog/Index/Task Ongoing.md` 汇总 `todo`、`in_progress`、`blocked`；`Worklog/Index/Task Done.md` 汇总 `done`、`cancelled`；两页由 MCP 从总索引刷新。
11. 每日日志以可读 Markdown 列表呈现，机器字段藏于 Obsidian 注释，并兼容旧日志行。

## 10. 实施状态与部署要求
